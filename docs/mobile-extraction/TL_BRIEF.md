# Mobile extraction: decisions needed from the team lead

One page. Status of the standardization of `mobile/idp-android` (the on-device Aadhaar/PAN extraction app) and the decisions only the team lead can make. Details: `STANDARDS_COMPLIANCE.md`, `docs/adr/`.

## Where we are
- The existing app was tidied to the IDP standards without adding features and without touching the servers or other teams' folders.
- 26 code files (25 tested; `ImagePreparation` needs a phone) were separated from the 2,660-line `MainActivity.kt` (now 1,322 lines): the Aadhaar, PAN, Indian DL and Indian passport checks, the model profiles and resize rules, the run-log and file rules, the output parser, the process-stats parser, and the llama.cpp launch arguments and request/reply JSON. PaddleOCR-VL support was removed from the app (not needed).
- 278 unit tests pass; lint (ktlint, detekt), Android Lint (0 errors) and both builds (debug, minified release) pass. One command runs it all: `mobile/idp-android/scripts/check.sh`.
- Security fixes: cleartext limited to the app's own local server, run logs kept in private storage.
- The app has run on a Galaxy M35 (Android 16): install, model loading, scans, the new run-log header and the disabled GPU switch work. The 21 checks in `PHONE_CHECKLIST.md` are not run systematically yet. Nothing is pushed or merged.
- One performance finding needs a decision (item 8 below): LFM2 scans take about 90 s with the libraries the pinned build script produces, against 25 to 36 s with the old libraries. Full evidence: `STANDARDIZATION_HANDOFF.md`, section 5.

## Decisions needed

**1. Does the on-device model stay? (the one that decides the most)**
- IDP-04 Ch. 3.4 describes two paths. Online: the phone uploads and the Python `extraction-service` extracts (line 265). Offline: ML Kit OCR, template rules, then the on-device SLM "only for fields that fail rules" (line 267). F-EX-15 (offline extraction, Phase 4) and open decision D-2 (on-device SLM and size per RAM tier) cover it.
- Our app is the on-device part only. Keep it, replace it, or drop it?
- The pure parts of the model call are already extracted and tested. The process start, HTTP calls and extraction flow stay in `MainActivity.kt` until a phone check can prove a move there. A decision to drop the on-device model would make the rest of that restructuring unnecessary.

**2. RAM tiers (D-2): dropped from this work.** Choosing the model per RAM tier is front-end (mobile app) work, not part of this standardization. Today the model is picked by hand and stays that way.

**3. Compose, Hilt and Room.** IDP-04 Ch. 3.1 expects Jetpack Compose (screens), Hilt (wiring) and an encrypted Room database. The app uses old-style screens and plain files. Moving to them is a rewrite of the UI and storage, not a cleanup. Do we leave it for now (our recommendation; ADR 0002 row 3) or plan it? It affects only the Android app, not the Python services.

**4. Release and signing.** Google Play with Play App Signing (the standard delivers the model by Play Asset Delivery) or another route? Who holds the upload key? The release build is minified (30.7 MB) and unsigned.

**5. The run log.** It keeps extracted fields as plain text in private storage, which is useful for testing. For a release build: keep, remove, or encrypt? (OBS-04, LLM-06.)

**6. Approval of nine ADRs** (all "Proposed"): 0001 keep llama.cpp for now; 0002 the deviations we are knowingly keeping; 0003 ktlint and detekt, with limits borrowed from the Python Standard; 0004 PaddleOCR-VL removed from the app and the test-only dependencies added; 0006 coverage measurement (JaCoCo) and a secret scan (gitleaks); 0005 prompt files versioned (`<name>.v1.md` with front matter) and a model registry added, as the Python Standard prescribes; 0007 the LFM2 input image is shrunk (PAN 500 px, Aadhaar, DL and passport 560 px); 0008 short prompts and small grammars for DL, passport and Aadhaar; 0009 the Qwen input image is shrunk to 560 px for DL and passport.

**7. Git.** When do we commit, push and merge (nothing is committed since `834025f`, nothing pushed)? Should `standards_docs/` and `CLAUDE.md` go into the repo? Naming: ticket ids and `feat/<TICKET>` branches are not used.

**8. LFM2 speed with the pinned llama.cpp build.** The new `libmtmd.so` (llama.cpp `000bee5`, upstream PR #27057) splits a PAN card into 15 tiles at our 128-token cap, about 3,800 image tokens instead of 112, so LFM2 `pan_full` takes 85 to 95+ s instead of 16 to 36 s. Qwen3-VL and MiniCPM-V are not affected. Options: **A** pin an older upstream commit (not tested); **B** shrink the LFM2 input in Kotlin (PAN 500 px, Aadhaar, DL and passport 560 px; command-line tests: 14 to 29 s; PAN 24/25 fields correct on five cards). **B is now in the working tree** (ADR 0007, 231 tests pass, nothing committed) and waits for your approval and an in-app phone check; **C** keep the old `libmtmd.so`, which has no documented source and cannot be rebuilt. Our recommendation: B, with accuracy re-checked on more cards and in the app. A further finding: LFM2 needs 2.2 to 2.7 GB of free RAM and stalls on a 5.5 GB phone when memory runs short (`ON_DEVICE_LATENCY_AND_ACCURACY_FINDINGS.md`). Detail and tables: `STANDARDIZATION_HANDOFF.md`, section 5.

**9. Which fields come back (ADR 0008).** To make DL, passport and Aadhaar scans 2 to 3 times faster the app now asks for fewer fields: DL licence number, name, DOB, issue date, validity (NT); passport number, name, DOB, gender, place of birth, issue and expiry dates; Aadhaar number, name, DOB, gender. Address, blood group, vehicle classes, TR validity, issuing authority, nationality and PIN are no longer asked for. Is that acceptable, or must the full set come back (about 33 s per DL scan with a shortened prompt, estimated, not measured)?

**10. Qwen image size for DL, passport and Aadhaar (ADR 0009).** 560 px: 15 to 25 s per scan but about 5 fields less per set than full size (DL 19/25 against 20/20, passport 28/34 against 33/34); full size: 60 to 75 s. In the Aadhaar smoke test 700 px read the address better than 560 px for 6 to 10 s more (3 cards, indicative); the owner kept 560 px on 2026-10-26. In-app on 10 Qwen and 7 MiniCPM-V scans (indicative): Qwen DL 7/10, passport 12/14, Aadhaar 11/12 on three cards; MiniCPM-V Aadhaar 8/8, DL 8/10, passport 8/14; 17 to 47 s each. Suggests MiniCPM-V for Aadhaar and Qwen for passport. The HIGH label means all fields were filled, not correct (decision for the team: a stronger confidence rule). The Aadhaar run in the app with Qwen's profile at 560 px gave a wrong number, name and PIN (checksum caught it, LOW); front-only cards get an invented address.

**11. RAM per model.** LFM2-VL 3B needs about 2.3 GB resident; on the 5.5 GB test phone it stalls (memory stall 27 to 54%, scans over 100 s) whenever other apps take memory. Qwen3-VL 2B and MiniCPM-V stay in RAM and run steadily. Which model ships on which RAM tier is the front-end team's decision (D-2). Qwen3-VL-8B on an 8 GB phone collapses from about 15 to about 0.3 tokens/s once its resident set exceeds available RAM (one exploratory run, not a full study; a KV-cache-quantization mitigation is written but unmeasured and sits uncommitted in `LlamaLaunch.kt`); a further re-test pass on the 6 GB phone (stop sequence, assistant-turn prefill, image-token cap, MiniCPM canvas crop) is scratchpad-only and not yet in the app. Both new: `QWEN3_VL_8B_LATENCY_FINDINGS.md`.

**Measured in the app on 2026-10-23 and 26** (answers scored against `data/india_docs/*/truth.md`): LFM2 DL 16/20, passport 13/14, Aadhaar 7/8, PAN 4/5, at 25 to 43 s per scan; Qwen PAN 10/10, DL 10/10 (full size, 34 s and 74.8 s), passport 6/7 (full size, 62 s). The same card gave the same answer in the app and on the test server in 10 of 11 comparisons. Detail: `ON_DEVICE_LATENCY_AND_ACCURACY_FINDINGS.md`.

## Future work and ideas (not built, none needs a decision today)

Written 2026-10-26 from the in-app runs and the test-server experiments. Nothing here is implemented.

1. **Choose the image size per scan (research).** The image-token cap is set when the server starts (`LLAMA_ARG_IMAGE_MAX_TOKENS`), so changing it per scan means a restart (about 8 s and a cold first scan); it is also only a ceiling (about 230 tokens are used at 560 px against a cap of 1024). The real lever is the resize edge in the app, which is free to change per scan: about 1 image token per 32x32 pixels, about 6 to 8 s per extra 100 tokens. Options: (a) judge the photo first (resolution, blur, text size; needs camera photos to tune); (b) **retry at a larger size (about 800 px) when the check fails** (Aadhaar at 560 px failed the checksum while 700 to 800 px read the number and PIN; the extra 10 to 25 s is paid only on bad scans); (c) keep today's fixed size per document type. Suggested: (b), after the confidence label is fixed, because wrong values that look plausible do not trigger a retry. LFM2 must keep a low cap because its preprocessor tiles large images (item 8 above).

   **Design if we build it (owner's idea, 2026-10-26): OCR confidence picks the image size.**
   - *Flow:* preprocess the photo, run a quick on-device OCR pass (ML Kit is the IDP-04 choice and an ML Kit library already ships in the build; whether the app uses it and how long a pass takes on the phone are not measured), read its confidence, then choose the model's image size: high confidence, small size (560 px); low confidence, larger size (700 to 800 px). The retry on a failed rule check stays as a safety net after the scan.
   - *What changes:* the resize edge (`ModelProfiles` constants, `ExtractionPlan.Plan.maxEdge`), per scan. Not the server's image-token cap, which is fixed when the server starts and stays a high ceiling (1024; LFM2 PAN 128 or 256).
   - *Known limits:* OCR confidence says the text is legible, not that the model will read it right, so it only picks the starting size. The threshold must be tuned on real camera photos (needs the evaluation set, item 5). The OCR pass adds time to every scan. Needs an ADR before building (new threshold, ML-07: thresholds in config, not literals) and a decision on the privacy of OCR text (no document content in logs).
   - *Order of work:* evaluation set, then stronger confidence label (item 2), then the retry, then OCR-first only if the retry alone costs too much time on bad photos.
2. **A real confidence label.** "HIGH" today means every field was filled in, not that it is right (Runs 21, 31, 33, 34, 38 were wrong and HIGH). Ideas: cross-field rules (validity after issue date on a licence, passport validity of 5 or 10 years, issue before expiry), a second read of the risky fields, agreement between two models.
3. **Image before instructions for Qwen.** On 5 licence cards at 560 px, image first read 23/25 fields and instructions first (the app today) 19/25, same speed. Not changed yet; passport and Aadhaar not measured image-first. Qwen's PAN profile was validated instructions first and should stay as it is.
4. **Best model per document.** From the in-app runs so far (indicative, 7 to 10 cards per model): MiniCPM-V on Aadhaar (12/12) and PAN (5/5), Qwen on licence and passport. Needs the evaluation set below before it is a rule, and the RAM-tier work (item 2 above) for which phone gets which model.
5. **An evaluation set and a CI gate (ML-11, ML-12).** Real camera photos (angles, glare, blur, large 3,000 to 4,000 px files) with confirmed ground truth, scored automatically per model and per image size. Today's numbers come from clean images, one run per card.
6. **Other known model errors (in-app, 2026-10-26).** LFM2 reads the father's name as the holder's on one passport (every run), MiniCPM-V gave different answers for the same passport image in server mode and one-shot mode (Runs 63 and 66, unexplained: compare the settings of the two paths), and Qwen's own Aadhaar profile takes 38 to 47 s because it asks for the address. Each needs a prompt or setting test and a re-measure.
7. **Front-only Aadhaar cards.** Qwen invents an address and PIN when the card has no address block (Run 27); the prompt or grammar needs a fix, then re-measure.
8. **Front-and-back cards, other layouts.** Cards photographed as front and back in one picture (Kerala licence, two-sided Aadhaar) lose accuracy at small sizes; a crop step or two reads may be needed.
9. **Test the 4B model** on the second phone (needs the connection, model file names, libraries and the phone's RAM and chip), and measure a size near 700 px for DL and passport.
10. **Result screen.** The output now lists only the extracted fields and the check result, and the run details sit in their own card. Left for the front-end team: proper field labels (for example "Date of birth" instead of "Dob"), the front-and-back output (still the old text), and showing the check result as a coloured badge.
11. **Build and release items already listed above:** 16 KB page alignment (the phone shows a compatibility warning), release signing, splitting `MainActivity.kt` (1,794 lines), a timeout on the one-shot command-line path (LLM-05).
